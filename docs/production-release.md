# Production release checklist

## Scope and acceptance

Target: one verified, trusted team in one shared workspace, preparing a release for a deployment at **up to 10 events/second**. No customer isolation, public registration, automated containment, unlimited scalability, or security certification is claimed. The existing local installation is not changed or exposed by preparing/testing this release.

Before deployment, an accountable operator must approve:

- [ ] Hosting/network access; keep database, Redis, backend, and optional Ollama private. The bundled HTTPS listener is still loopback-only.
- [ ] Exact hostname/origin, trusted TLS chain, certificate renewal and expiry alerts; verify Secure cookies, WSS, HSTS, Host/Origin rejection, and blocked private paths.
- [ ] Secret-manager delivery, unique credentials, encrypted storage, and separately recoverable MFA key. Do not paste credentials into chat or commit them.
- [ ] Account review, identity verification and private starter-password delivery, MFA enrollment, recovery-code custody, and offboarding. Existing migration preserves account passwords; review old starter-password use explicitly.
- [ ] Reliable server/authenticator time synchronization and clock-skew alerts; JWT validity and TOTP verification depend on accurate time.
- [ ] Backup destination/schedule, age recipients and offline recovery identities, recovery-point/time objectives, and a successful off-host restore drill.
- [ ] Raw-log retention and legal holds. Evidence, audit history, source receipts, and collector quarantine require a separately approved lifecycle; they are not automatically erased.
- [ ] External availability, failed-login, stale-source/collection-gap, collector quarantine, disk-growth, backup-age, and certificate alerts with a tested notification channel/runbook.
- [ ] Separately controlled append-only/immutable audit storage and independently preserved export anchors.
- [ ] Measured representative load/bursts and projected retained-data size. 10 EPS continuously is 864,000 records/day; a short fixture test is not validation at that retained size.
- [ ] Current dependency **and container OS-layer** vulnerability review, release-image digests, patch policy, migration rehearsal, rollback backup, and independent security review/penetration testing.

Use the [operator acceptance record](operator-acceptance.md) to assign owners, retain private evidence, and make the final go/no-go decision. Preparing or publishing this release does not approve deployment or change the existing installation.

The [security/reliability follow-up](security-improvements.md) describes new database identities, passkeys, expiring collector keys, outbox/egress controls, clock guards and their separate validation status. Earlier passing evidence below does not automatically validate later changes.

## Deployment artifact

Fresh configurations generated by `scripts/init_env.py` contain an MFA encryption key. For an existing installation, generate one privately with `Fernet.generate_key()` and add it deliberately; never rotate it without decrypting/re-encrypting enrolled seeds or an approved account recovery plan.

Use these files together, against the explicitly selected private environment/database:

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml -f docker-compose.production.yml config --quiet
```

The production overlay enforces production flags, resource/process limits, graceful backend shutdown, and log rotation. Application base images are digest-pinned; the web-server build applies Alpine security updates and the backend removes pip/setuptools from its runtime. The production PostgreSQL build updates Alpine packages, removes the old Go-based `gosu` binary, and adapts the upstream entrypoint to use `su-exec`; rehearse initialization and existing-volume restarts on every update. Redis is digest-pinned and uses `noeviction`; memory exhaustion can deny rate-limited requests and must alert an operator. Budgets are starting limits, not a hardware sizing guarantee. Configure the assistant explicitly (`offline` is recommended until privacy/egress review). Never mount a Docker socket into the application. Do not apply the disposable release-test override to a running installation.

Take a verified backup before migrations. Migrations preserve existing identities, password hashes, roles, collector keys, and event IDs. Production requires MFA for old accounts too; pre-enrollment access is restricted to account setup. A downgrade after raw-log retention can fail because receipt tombstones intentionally outlive events; restore a reviewed pre-upgrade backup rather than deleting receipt protection.

## Repeatable release validation

Install the backend requirements in an isolated Python environment and have Docker Compose 2.24.4+, OpenSSL, age, and age-keygen available:

```bash
.venv/bin/python scripts/release_check.py --seconds 120
# Selected capacity profile: one day's volume, then a ten-minute API soak.
.venv/bin/python scripts/check_runner_clock.py -- .venv/bin/python scripts/release_check.py --seconds 600 --history-events 864000
```

This creates a randomly named disposable project and private artifacts under `/tmp/opencode`, not the live environment. It uses ports **18080/18443**, a dedicated PostgreSQL database, and an independently trusted test CA (no disabled TLS verification). It tests production login/password/MFA gates, credential replay, blocked paths/origins, 10 EPS with concurrent dashboard reads, persisted detection results, PostgreSQL restart, Redis failure/retry, and encrypted backup/restoration. Gate: no ingestion/read errors, at least 9.5 acknowledged EPS, ingestion and dashboard p95 <1 second and maximum <5 seconds, exact persisted totals, restored counts/schema and streaming SHA-256 table-content fingerprints, rejection of corrupt archives, and refusal to replace an existing database. Default 120 seconds is a bounded smoke/load test; use a longer soak and representative preloaded history before deployment.

The selected larger fixture directly seeds **864,000 quiet synthetic authentication records and receipt placeholders** across the prior 24 hours, then measures 6,000 fresh API deliveries over 600 seconds. Its eight address/host groups also appear in the incoming workload. Direct seeding tests retained-data pressure, not historical ingestion, detection, or replay correctness; those paths are tested by fresh API records. Exact persistence/restore counts include seeded history. Dashboard totals describe a rolling 24-hour window, so older history can naturally leave that window during the soak. Longer runs rotate the fixture session without extending token lifetimes. One day's volume is not validation of seven days of continuous 10 EPS, mixed workloads, bursts, or optional model inference.

For interruption-resistant local artifacts, use `--output-dir .release`; this directory is excluded from Git and Docker build contexts. Keep load runs separate from builds, vulnerability scans, and regression suites so the generator is not competing with those checks. Scheduling delay counts toward the latency gate; the report also separates scheduling delay and request time for diagnosis. Preserve failed reports rather than treating a successful retry as proof that a failure was fixed.

With `--keep`, follow up using `scripts/scan_release.py --artifact-dir <private-test-directory>` (Trivy required) and `scripts/browser_release_check.py --artifact-dir <private-test-directory>` (certutil and installed Playwright Chromium required). The scanner checks the **exact five runtime image IDs**, including OS and language packages, and fails on any HIGH/CRITICAL result without a blanket ignore list. Browser checks use a temporary HOME/NSS trust database and the private fixture credentials; they do not change the operator's trust store or disable TLS verification. CI is configured to run both database regression suites with clock-step observation and the one-day/ten-minute capacity profile; a source change is not CI-validated until its actual run is inspected. The runner observer rejects observed clock steps of 50 ms or more; it does not adjust time or relax application JWT/TOTP verification. Optional Ollama is outside the five-image profile and needs a separate scan/review if enabled.

Only `report.json` and `container-scan-summary.json` are selected as public fixture-only CI artifacts. Generated `.env`, certificates/private keys, backups, browser credentials, traces, and captures stay private. The runner stops only its own disposable project and preserves volumes for review; it never runs `down -v` on the live installation. `--keep` leaves the disposable stack running for further checks.

## Backups and recovery

Install age from a trusted source. Use an approved public recipient; keep the matching private identity offline, mode 0600. Example commands use placeholders, not real credentials:

```bash
python3 scripts/backup.py --project sentinelx --env-file .env --compose-file docker-compose.yml --compose-file docker-compose.https.yml --compose-file docker-compose.production.yml backup --database sentinelx_live --recipient age1YOUR_APPROVED_PUBLIC_RECIPIENT --output /secure/backups/sentinelx.age
python3 scripts/backup.py --project sentinelx --env-file .env --compose-file docker-compose.yml --compose-file docker-compose.https.yml --compose-file docker-compose.production.yml restore-drill --database sentinelx_restore_drill --identity-file /secure/offline/backup.agekey --input /secure/backups/sentinelx.age
```

The restored database is for isolated review, not an automatically activated replacement. Validate evidence, accounts, source configuration, matching MFA keys, and collector recovery before switching connections. Dumps include sessions and collector hashes: treat them as sensitive. A real incident restore should revoke old human sessions and deliberately review collector key/checkpoint reconciliation.

## Retention and account recovery

Run commands in the backend environment you deliberately select. Start with a dry-run:

```bash
python -m app.operations retention --days 30
```

An explicit `--apply --confirm-database <exact-selected-database>` enables PostgreSQL writes. A run removes at most 1,000 eligible events (adjustable, maximum 10,000) plus expired refresh records. Both occurrence and receipt timestamps must be old; minimum retention is seven days, beyond the maximum one-day rule window. Alerts, linked investigation evidence, and incident-associated receipts protect events. No investigation/note/audit/source key is deleted. Source receipts retain stable acknowledged IDs/payload hashes after raw events disappear, so retries still deduplicate rather than resurrect logs; counters are lifetime deliveries, not retained row counts. Backfilled detection older than retained raw history cannot recover deleted evidence. Schedule only after policy approval and monitor backlog/storage growth.

If an enrolled person loses both authenticator and recovery codes, independently verify their identity, then use `python -m app.operations reset-mfa --user-id <id>` to preview. Add explicit `--apply --confirm-database <database>` only after approval. This revokes sessions and requires fresh MFA enrollment in production; it does not reset their password, role, or evidence. There is no self-service bypass or emailed reset.

## Availability and audit exports

```bash
python3 scripts/health_check.py --origin https://sentinelx.example
python -m app.operations export-audit --output /secure/audit/batch.jsonl --after-id 0
```

Readiness verifies PostgreSQL/Redis and production clock-step observation, not completeness of monitoring or absolute time synchronization. The external health helper additionally warns before trusted-certificate expiry. Connect failures to an actual alert channel; source health and collector gap/quarantine notices require separate checks.

Audit export is read-only, exclusive-create, mode 0600, ordered by ID, and SHA-256 chained. Preserve the reported cursor/hash outside the host; pass `--after-id` and `--previous-hash` for the next batch. Retry interrupted exports from the last externally acknowledged anchor. This is **not tamper-resistant local storage**: only independently anchored copies in a separately controlled immutable destination provide that boundary. Protect audit exports as sensitive data; no publication/upload is automatic.
